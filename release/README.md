# ContextDB release engineering inputs

This directory is release-policy input, not proof that Alpha, Beta, or v1 has shipped.

`local-mcp-profile.json` defines a separate Windows x86_64 developer-preview package. It is
verified by `tools/local-mcp-preview`, remains outside the formal package matrix, and always
records `release_ready=false` and `m18_alpha=false`.

The local profile's generated dependency evidence is
`contextdb-local-mcp-supply-chain.json`, `contextdb-local-mcp.cdx.json`,
`THIRD_PARTY_NOTICES.txt`, and `rust-runtime/`. The manifest binds the exact locked
listener-free graph and every artifact hash. Regenerate and review it using
`tools/local-mcp-preview/generate_supply_chain.py`; see
`docs/release/third-party-dependencies.md`.

`package-matrix.json` is the canonical package/target inventory consumed by the
standalone verifier in `tools/contextdb-release`. It intentionally records the
difference between source that exists, packaging that can be inspected
statically, runtime proof, and external publication proof.

The same matrix is consumed by the offline `assemble-bundle` command together
with an explicit `contextdb.release-bundle-input/v1` manifest. The input
manifest is generated by the release operator after builds finish; it names and
hashes every artifact, proof, build recipe, and related evidence file. The
assembler copies existing bytes only and cannot turn source presence into a
release claim. See `docs/release/artifact-contract.md` and
`tools/contextdb-release/README.md` for the command and trust boundary.
`bundle-input.example.json` is schema-valid documentation only: zero hashes,
zero sizes, a dirty all-zero commit and explicit limitations ensure it is not a
release candidate or a source of fabricated evidence.

`documentation-matrix.json` is the public documentation-category inventory. A
path's existence is only source evidence; the matrix separately records
completeness, runtime verification, publication verification, and exact gaps.

The current release policy is:

- Linux x86_64, Linux arm64, and macOS arm64 are required v1 targets.
- Windows x86_64 is best effort and its failures must remain visible.
- Alpha requires the declared preview artifacts and exact package verification.
- Beta additionally requires the declared security, benchmark, and
  required-platform evidence.
- Stable requires the complete signed artifact, provenance, installation,
  benchmark, and publication set.

The matrix is necessary but insufficient. A release bundle must also contain a
schema-valid artifact manifest, proof index, canonical `SHA256SUMS`, detached
signature set, version manifest, required artifacts, install receipts, and the
evidence referenced by the roadmap ledger. The verifier fails closed when any
release dependency or required platform proof is absent.

Production signatures require an independently trusted public key. Shipping a
public key beside a bundle does not make that key trusted. Test keys are accepted
only by the verifier's explicit contract-test profile and can never produce
`release_ready: true`.

External runtime/publication/SBOM/provenance evidence is accepted only through a
digest-pinned `contextdb.release-external-receipt-set/v1` landing zone processed
by `intake-receipts`. The landing zone is disjoint from the subject bundle and
must contain exactly the declared files. Acceptance is quarantine validation,
not live retrieval, custodian trust, a copied bundle member, or a passed gate.

Upgrade, rollback and disaster-recovery receipts are produced from exact old/new
bundle pairs with `operational-drill`; see `deploy/release`. The manual
`release-candidate.yml` workflow creates unsigned, non-publishing candidate
inputs for the native platform matrix under either repository visibility. It
deliberately has no signing, registry publish, GitHub Release, Docker build/run,
or roadmap mutation step.
Its SBOM/provenance files are unsigned, self-asserted candidate metadata; they
are not final supply-chain attestations and cannot satisfy a release gate.
